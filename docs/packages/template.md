# Package page template

Every package page uses the same six sections in the same order, so a reader who has used one page
knows where to look on the next. Copy the skeleton below, replace the `<placeholders>`, and delete the
guidance comments. Keep a section even when it is short; write "None yet." rather than removing it.

## Rules

- **One package per page**, named after the package, under `docs/packages/`. Add it to `nav` in
  `mkdocs.yml` and to the table in the [package index](index.md).
- **Open with two sentences**: what the package does, then who needs it. Link back to the index for
  the other packages in the same stack.
- **Commands must work as written.** Use `pip install --pre` while the package is in alpha. CI runs every
  Python or shell block that follows a `<!-- sample: run -->` comment against the published packages
  (`scripts/check_samples.py`), so mark each block that can run on its own. Blocks on one page share a
  scratch folder and run in page order. Leave fragments, and blocks that need a database or a server, unmarked.
- **Link to the demo.** Each package page has a `Demo` row that links to its page on the demo site. CI checks
  the link (`scripts/check_demo_links.py`), and fails external links that return 404 (`scripts/check_links.py`).
- **Do not hand-write API reference** for Python packages. It is generated by mkdocstrings from
  docstrings in the package's repo, so fix docstrings there. For JavaScript packages, link to the
  generated reference or the exported types.
- **Keep legal decisions out.** Describe what the code records and enforces. Leave what the notice
  must say and how long to keep data to the reader and their counsel.

## Skeleton

````markdown
# <package-name>

<What it does, in one sentence.> <Who needs it, in one sentence.>

| | |
| --- | --- |
| Install | `pip install --pre <package-name>` |
| Version | <current version> |
| Requires | <Python / Node / framework versions> |
| Source | <link to repo> · [Changelog](<link>) |
| Demo | [Try it on the demo site](https://dpdpkit-demo.onrender.com/packages/<demo-slug>) (fictional data; can take a minute or more to wake) |

## Install

```bash
pip install --pre "<package-name>[<extra>]"
```

<!-- Extras and what each adds. Required system packages or drivers. Supported versions, if they
differ from the package index. -->

## Quickstart

<!-- The shortest path to one working result. Numbered steps, each with code the reader can paste.
End with a command or request that shows it worked. Link to the full guide rather than repeating it. -->

## Configuration

<!-- Every setting the reader may change: name, type, default, what it does. A table is usually best.
Say which settings come from the environment and which from dpdpkit.yaml or code. Mark settings that
must be set before production. -->

## API reference

<!-- Python: an mkdocstrings block pointing at the module, for example
::: dpdpkit.fastapi.DPDPKit
or a link to the page under reference/python/. JavaScript: link to the exported types. REST-only
packages: link to the REST contract. -->

## Troubleshooting

<!-- Symptom, cause, fix. Use the exact error text or code the reader will see, so it can be found by
search. Include "nothing happens" cases such as a scheduler that is not running. -->

| Symptom | Cause | Fix |
| --- | --- | --- |
| <error text or behaviour> | <why> | <what to do> |

## Upgrading

<!-- Start with the supported upgrade path and which packages must move together (for example
adapters need a matching dpdpkit-core minor). Then one subsection per release with breaking changes,
newest first: what changed, what to do, and whether a database migration runs. Link to the changelog
and to Versioning and deprecation. -->

See [Versioning and deprecation](../reference/deprecation.md) for how breaking changes are announced.
````

## Section guide

| Section | The reader is asking | It must contain |
| --- | --- | --- |
| Install | "What do I run?" | Install command, extras, version requirements |
| Quickstart | "Can I see it work?" | Pasteable steps and a visible success check |
| Configuration | "How do I change it?" | Each setting with its default, and production-required ones marked |
| API reference | "What exactly does this call do?" | Generated reference or a link to it |
| Troubleshooting | "Why did this fail?" | Symptom, cause and fix, using real error text |
| Upgrading | "Is it safe to move to the next version?" | Upgrade order, breaking changes, migrations |
